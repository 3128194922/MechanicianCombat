## 1. 评估结论

MechanicianCombat 具有移植到 Minecraft Forge 1.20.1 的技术基础：主要前置已找到对应发布物，模型、贴图、动画和大部分业务规则可以复用。但它不是修改版本号即可运行的项目，而是同时跨越 **Fabric → Forge、Minecraft 1.21.1 → 1.20.1、Java 21 → 17、Yarn → Mojang official** 的移植。

工作重点依次为：注册与生命周期、物品数据和菜单、服务端战斗与网络、客户端动画和相机、前置接入与 Mixin。单纯批量改名不能完成这些工作。

目前可以确认源项目规模、接口适配已编译、前置发布物及其元数据；最新候选包已通过部分关键运行场景，但**移植仍未完成**：剩余 UI、菜单安全、其余玩法矩阵与联机视觉同步仍需验收。

已确认的主要玩法决定：

1. **风弹方向已确认**：参考 GitHub 已有 Forge 1.20.1 项目，在本项目内实现风弹，不增加风弹模组前置；获取方式交给整合包配置配方或掉落，本模组不内置配方。源码比较见 [风弹参考项目与实现方案](风弹参考项目与实现方案.md)。
2. **忠诚附魔支持已确认**：用户要求移植忠诚，熔铁弩矢须支持忠诚回收；不自动开放其他附魔。关于撞方块消失，用户要求按原项目完全复刻，因此保留 50% 消失，只有存活的弩矢能够返回。

本报告区分已确认决定与建议；用户已经批准的前置方案、内置风弹方向和忠诚支持不重复询问。

**可行性结论为有条件可行，实施仍未完成。** 目标源码已编译，当前产物可复现，正式客户端和专服可启动；双人登录、枪械实射、关键数据重启读回已验证，但完整玩法、界面与前置回归尚未验收。验收证据及边界以 [移植进展](PROGRESS.md) 为准。

### Accessories 的额外核查

- 发布 API 返回的 dependencies 数组为空，但 JAR 元数据明确要求 `cloth_config >= 11`，因此安装清单不能只依赖网页/API 标签。
- JAR 内置 Endec 0.1.8、Endec Gson/Netty 模块、MixinExtras Forge 0.3.5，以及少量 Forge 版 Fabric API 模块。这部分已取得用户追加批准。
- 本方案不额外安装 Connector，也不把本模组继续写成 Fabric 代码。主项目仍应使用 Forge 原生注册、网络和事件。
- 其 JAR 内版本字符串为 `1.0.0-beta49+1.20.1`，与文件名中的 `beta.49` 有细微差异；依赖范围必须按真实元数据核实。

### 不应机械沿用的源前置

源包列有 owo-lib、Forge Config API Port、AzureLib 等。当前核实的六个目标 JAR 没有声明需要额外安装这些模组，因此不应直接照搬源 Fabric 安装列表。若目标 API 或运行验证后发现需要，应记录具体依据；超出已有批准范围的新增依赖仍需确认。

CustomSkinLoader 在源说明中为可选项，不应成为强制前置。也没有理由在当前方案中擅自替换为 Curios。

### 5.1 网络和状态

共有 13 个源消息类：开火、装填、专注、翻滚、切换弹种、打开弹药环、背包发射、背包发射反馈、背包状态、枪械状态、命中标记、演示状态和音效。

迁移不能只做到“消息能收发”，还要保持：

- 服务端判断持有物、弹药、冷却和当前动作，客户端仅发送操作意图。
- 客户端提交的枪口坐标、方向和目标必须做有限值、距离和状态校验。
- 客户端/服务端方向固定；双向音效消息按接收侧校验，不能允许任意广播。
- 登录、重新追踪玩家、重生、换维度和断线都有正确的状态同步或清理。
- 协议不匹配时明确拒绝，不能依赖旧协议“包尾字段不存在就默认值”的做法掩盖差异。

### 5.2 数据和物品安全

枪械数据需保留 `tkgun_ammo`、`Selected`、`tkgun_mag`、`tkgun_mag_ammo`、`tkgun_mag_version` 的业务含义。背包需保留核心、发射器类型及组件槽位信息。

重点是区分“新物品没有数据”与“弹匣已打空”，以及两把枪的独立数据。菜单还要覆盖换手、丢弃、Shift 点击、关界面、断线和改装台被破坏，避免复制或丢失物品。

### 5.3 资源转换

- `data/*/recipe` 改为 `recipes`；`loot_table` 改为 `loot_tables`；`tags/item` 改为 `tags/items`。
- 已查到背包染色配方的结果使用 `id`，1.20.1 应转换成 `item`，仅改目录不够。
- `damage_type` / `tags/damage_type` 不应一起机械复数化。
- 1.21 的 `enchantable/trident` 标签不能直接实现 1.20.1 的附魔兼容。
- 新版 GUI sprite 绘制需适配；模型骨骼名、动画名、声音 ID 和纹理路径尽量保留。
- 建立 1.20.1 `pack.mcmeta`，pack_format 为 15；以 `mods.toml` 取代 Fabric 入口元数据。
- 首次移植优先复用已导出的美术资源，不运行含作者本机路径的导出脚本。

## 6. 玩法规格与待验证边界

### 6.1 风弹在 1.20.1 不存在

**后续决定（2026-10-25）：用户已选择在本项目内制作风弹，并要求查找 GitHub 的 Forge 1.20.1 回移实现作参考。** 已完成两个候选的固定提交源码调查，主要参考 Just Trial Spawners；具体依据、静态问题和接入方案见 [风弹参考项目与实现方案](风弹参考项目与实现方案.md)。

证据：源 `item/BackpackLauncherRules.java:23` 允许 `Items.WIND_CHARGE`；`TkGunServer.java:1652` 起创建 `WindChargeEntity`，并使用风弹声音。

目标规格：使用自有 `tkgun:wind_charge` 标识，保留背包发射入口、源初速度 1.6 格/tick，以及成功生成后消耗 1 个副手风弹和 1 次充能的规则。配方或掉落由整合包配置，本模组不内置配方。碰撞、风爆、同步与视觉由本项目实现；不注册为 `minecraft:wind_charge`，不新增参考模组或其运行前置。

参考项目仅提供代码结构和算法依据。按源版玩家风弹建立对照，分别验证直接命中、击退、遮挡、反弹、方块交互与落伤保护；任何简化须明确记录，不能用简化参考实现代替完整验收。当前仅报告阶段。

### 6.2 忠诚附魔与原有消失规则

**用户决定（2026-10-25）：“附魔忠诚移植”。** 在此前熔铁弩矢附魔问题的上下文中，记录为目标版支持熔铁弩矢忠诚附魔。不扩大为恢复全部三叉戟附魔；穿刺、引雷等不因本次决定自动开放，激流仍禁用。Minecraft 1.20.1 已有忠诚附魔，本项目适配物品和弹体，不另建同名附魔或增加前置。

#### 源码证据

- `item/MoltenTridentItem.java`：不可附魔、附魔能力为 0；初始化和物品 tick 均移除附魔数据。
- `entity/MoltenTridentEntity.java`：构造弹体与读取武器物品时再次移除附魔；虽然保留同步忠诚等级的代码，正常构造路径得到的物品已无附魔。因此仅移植忠诚字段或注释不能让功能生效。
- 同一弹体的 `onBlockHit`：服务端有 **50% 概率 discard**；附魔恢复后仍可能在忠诚返航前销毁。
- 同一弹体的 `tick`：穿透命中后清除 `dealtDamage`，注释明确用于防止忠诚在命中第一个实体时立刻折返。不能为接上忠诚而默默取消原穿透行为。
- `mixin/BackpackLoyaltyPickupMixin.java`：仅对属于该玩家、带背包发射标记且发射器仍有效的忠诚三叉戟，尝试优先返还副手；副手为空或相同物品及数据且未满才接收，否则继续原拾取路径。
- `TkGunServer.restoreBackpackChargeAfterLoyalty`：上述副手接收成功后，冷却期会清除冷却并恢复满充能；非冷却期最多补一次充能。不能把原规则误记为所有回收都只补一次。

#### 后续适配要求

1. 使用 1.20.1 原版忠诚及其等级；让物品存储、弹药模板、弹体构造、存档和回收全过程保留忠诚信息。附魔获取入口应在实施前明确记录，不能只支持命令写入却宣称正常生存可附魔。
2. 对手持投掷、背包发射、枪械发射三条现有生成路径逐项验证；不能因共享实体只验证手持路径。枪械回收不得额外自动补满弹匣或重复退款。
3. 背包副手优先回收及充能规则按上述源代码适配，校验所有者和发射来源，成功回收只结算一次；副手不同附魔等级的堆叠不能混合。
4. 验证穿透阶段、返航触发、返航途中碰撞/伤害及已命中集合，避免返航每 tick 重复伤害。区分源有行为与新增改变，有玩法差异先确认。
5. 无忠诚与忠诚 I/II/III 分别验收；覆盖背包满格、副手占用、创造模式、所有者死亡/离线/换维度和实体重新加载。没有实测前不宣称全部边界已正确处理。

#### 撞方块消失规则已确认

用户对该问题答复“按原有项目的情况完全复刻”，因此按源码保留撞方块后 50% 消失，不对忠诚弹体增加豁免。该答复针对消失规则；与此前已要求的忠诚支持同时记录，不能又照搬清除所有附魔的代码而使忠诚失效。穿透期间避免首个实体命中立即折返、背包回收与充能规则均按源行为对照。当前仅报告阶段，未修改物品或实体实现。

### 6.3 原版自身尚未验证的视觉问题

`SOURCE_HANDOFF.md` 已列出自动炮塔 C3 锁定方向、滚转、不同骨架/越肩视角位置和切换平滑度待验证。移植成功不能自动消除这些问题；应独立记录“源版待验证”和“移植引入的回归”。

### 7.1 恢复实施时的第一批工作

1. 记录主项目当前文件状态，审查现存转换稿和日志；保留用户改动，不重跑覆盖式迁移脚本。
2. 对照固定工具链和依赖锁复核构建配置，先得到当前编译结果，再建立按模块归类的问题清单。旧 238 条错误只作历史证据。
3. 建立注册 ID、13 个消息和 20 个 Mixin 的对应清单，标明源位置、目标入口、运行侧和验证方式；不通过排除源文件或关闭注入掩盖缺失。
4. 按 R1–R5 推进，每次只把有相应证据的项升级为“编译通过”或“运行通过”。涉及新增依赖、削减功能或改变玩法时，仅暂停受影响部分并提交方案。

### 7.2 风险与处理要求

| 风险 | 可能后果 | 处理与验收要求 |
| --- | --- | --- |
| 映射名正确但 API/行为不同 | 编译失败或运行时行为偏差 | 逐调用点核对目标源码；以有源码构建和行为测试确认 |
| 物品数据迁移与容器转移不完整 | 空弹匣复活、附魔丢失、复制或吞物品 | 两把枪独立、重登、关闭/断线及异常槽位专项检查 |
| 客户端代码进入专服加载链 | 专服启动崩溃 | 前置和渲染隔离；独立专服启动，不以单人游戏代替 |
| 网络消息缺少状态约束 | 越权发射、重复扣弹、远程操作菜单 | 服务端验证输入与动作，双人环境复核 |
| 忠诚与背包返还重复结算 | 弹药或充能复制 | 按所有者、来源与拾取成功条件结算一次，保留原消失规则 |
| 风弹参考源码被当作完整原版实现 | 击退范围、反弹或落伤规则偏差 | 采用专项对照矩阵；不继承参考工程额外依赖 |
| 动画、相机和注入静默失败 | 功能存在但操作/视觉错误 | 注入日志与各视角实机结果共同留证 |

## 8. 验收标准

| 检查项 | 必须观察到的结果 |
| --- | --- |
| 构建与发布 | clean build 通过，JAR 确属 Forge 1.20.1；没有原 Fabric 编译副本或游戏 JAR 被打包 |
| 侧别 | 客户端与独立服务端均启动；服务端不加载客户端类 |
| 注册与资源 | 物品、配方、方块掉落、声音、动画和贴图可用，无关键加载错误 |
| 枪械 | 腰射/专注容量正确，空弹匣不能自动补满，装填/过热/闪避状态约束正确 |
| 持久化 | 两把枪独立；打空、换枪、丢弃捡回、退出重登后数据一致 |
| 容器 | 仅有效玩家/距离可操作；Shift 点击、换手、关闭和断线不复制或吞物品 |
| 全部弹种 | 各弹种伤害、范围、击退、追踪、回收按确定的规则对照；附魔及风弹按用户决定验收 |
| 忠诚回收 | 三种发射路径保留忠诚等级与物品数据；副手优先和背包充能正确；无重复返还、额外自动补满弹匣或重复伤害；撞方块保留 50% 消失 |
| 内置风弹 | 背包速度 1.6 格/tick，成功生成仅扣 1 个风弹及 1 次充能；碰撞/风爆只结算一次，击退与联机同步正确；无内置配方，可由整合包按 ID 配置获取 |
| 背包与炮塔 | 装备、核心/发射器安装、锁定、充能、冷却、目标失效及自伤规则正确 |
| 输入与视觉 | 默认及重新绑定按键均可用；翻滚/滑铲/快速专注时序正确；各视角位置合理 |
| 联机 | 两人分别操作和观察，动作/声音/弹体同步；重生/换维度/重新追踪无遗留状态 |
| 非法输入 | 无枪开火、非法槽位、非有限坐标、失效目标或高频请求不能越权或导致崩溃 |
| Mixin | 核对所有保留注入实际生效；不能通过降低 required/require 掩盖失效 |

纯逻辑使用不新增第三方测试库的检查；世界交互使用 Forge 1.20.1 GameTest 或实际游戏测试。编译通过、单人通过、专服通过和双人通过必须分别记录。

### 8.1 证据与发布门槛

- 每条验收记录包括：测试包版本及 SHA-256、JDK/Forge/前置版本、测试场景与操作、期望结果、实际结果、日志或截图位置、日期和状态。未执行填“未测”，不填“通过”。
- 随机消失规则应同时核对服务端判定路径与足够样本的运行结果；单次返回或消失不能证明 50% 概率正确，返航和销毁两个分支都需覆盖。
